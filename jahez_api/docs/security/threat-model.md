# Threat Model

**Status:** reviewed in the Phase 9 first pass and extended for Phases 4–6 (2026-10-03). It covers the implemented surface: authentication, accounts, factories and providers, the audit log, the platform foundation, the service catalog and provider directory, factory classifications, and the marketplace (requests, negotiation, offers). It is extended in each phase. Tested controls are listed in [security-test-matrix.md](security-test-matrix.md), and review findings in [findings.md](findings.md).

## Assets
- **Accounts and credentials:** password hashes, API tokens, password reset tokens.
- **Tenant data:** factory and provider profiles, factory classifications. Later: roadmaps, evaluations, contracts and financial records.
- **Commercially sensitive negotiation data (Phase 6):** which providers a factory approached, each negotiation's messages, and offer terms and prices. Competing providers must never see each other's.
- **Provider contact details** (representative, job title, email, phone): shown to the provider itself and IMC, not in the directory ([OQ-37](../open-questions.md#oq-37)).
- **Personal data:** names and emails of staff (see [OQ-25](../open-questions.md#oq-25) for data protection).
- **Availability** of the platform, and especially of IMC administration.

## Actors
- Anonymous internet clients.
- Authenticated factory and provider members, who may be curious or malicious toward other tenants.
- IMC administrators (trusted, but their accounts are high-value targets).
- Operators with database, log or backup access.

## Trust boundaries
Client → API (TLS, terminated at the proxy) → application → MySQL / queue (database driver) → mail provider.

## Threats and controls

| # | Threat | Control (status) |
| --- | --- | --- |
| T1 | **IDOR/BOLA:** a member changes an ID to read or modify another tenant's record | Policies on every record route; ownership taken from the user's own organization link; cross-tenant access returns **404**; authorization runs before validation (**implemented, tested**) |
| T2 | **Function-level escalation:** a member calls admin endpoints, or sets their own role | Permission checks; role and organization are not mass-assignable and are ignored on update; DB CHECK on role↔organization (**implemented, tested**) |
| T3 | **Account enumeration** through login, forgot-password or reset responses and timing | Identical messages; a fixed-cost dummy hash comparison for unknown emails; forgot-password work moved into the queue (**implemented, tested**). Residual: network jitter and DB-cache effects are not measured. |
| T4 | **Credential stuffing / brute force** | 5 failures per minute per email+IP, 20 per 15 minutes per account, 60/min per IP overall (**implemented, tested**). The throttle keys are hashed, so the database cache store counts long emails too (FC-02). Residual: an attacker can lock an account out for 15 minutes (accepted trade-off, OQ-33). |
| T5 | **Token theft or replay** | 8-hour expiry; revocation on logout, reset and deactivation; tokens of deactivated users are rejected on every request; tokens are stored hashed by Sanctum (**implemented, tested**). Residual: no refresh-token rotation; client-side storage is the client's responsibility. |
| T6 | **Reset tokens leaked from storage** (queue tables, failed jobs, logs, backups) | Tokens are created inside the jobs and never stored in payloads (**implemented, verified end-to-end**). Production must not use `MAIL_MAILER=log` (**documented**). |
| T7 | **Weak passwords / silent bcrypt truncation** | Minimum 12 characters, maximum 72 bytes (**implemented, tested**). Breached-password check not enabled (OQ-33). |
| T8 | **Administrator lockout** (self-deactivation, or mutual deactivation) | Self-deactivation refused; a row lock keeps one administrator active; console recovery with `app:create-admin` (**implemented, tested**) |
| T9 | **Information disclosure in errors** | One JSON envelope; fixed 404/405/429 messages; no traces or SQL when `APP_DEBUG=false`; unique-key violations return 409 without SQL (**implemented, tested**) |
| T10 | **Mass assignment** | Explicit `$fillable`; `validated()`/`safe()->only()`; strict mode in non-production throws on discarded attributes (**implemented, tested**) |
| T11 | **CSRF / CORS abuse** | Bearer-only API (no cookies, so CSRF does not apply); no web routes and no Sanctum CSRF-cookie route ([ADR-013](../decisions/ADR-013-api-only.md)); CORS deny-by-default allow-list on `api/*` only (**implemented, tested**) |
| T12 | **SQL injection** | Eloquent/bindings only. The audit-log filters are allow-listed or type-checked, and the pagination cursor is validated (**implemented, tested** with SQL payloads). Phase 4–6 lists allow-list their filter keys, filter values and sort keys (422 otherwise); the directory's name search is a bound `LIKE` with `%`, `_` and `\` escaped (**implemented, tested, mutation-verified**). |
| T13 | **Known-password demo accounts in production** | Demo and test accounts are created only in local/testing, with the guard inside each seeder (**implemented, tested**) |
| T14 | **Spoofed client IP** to dodge rate limits | `X-Forwarded-For` is trusted only from `TRUSTED_PROXIES` (**implemented, tested**) |
| T15 | **Dependency vulnerabilities** | `composer audit` / `npm audit` each phase (**run; 0 advisories**). Automated CI scanning is pending a remote ([OQ-28](../open-questions.md#oq-28)). |
| T16 | **Secrets in the repository** | `.env` is ignored; Postman files hold no real secrets; the staging example is empty. A pattern-based scan of tracked and new files found no secrets (**Phase 9**). `gitleaks` over the full history of all branches found no leaks (**2026-10-03**). Re-run it before each release ([testing strategy](../testing/strategy.md#2-commands)). |
| T17 | **Missing audit trail** for security events | Append-only audit log of logins, failures, throttling, resets, account and organization changes; each entry is written in the same transaction as its change; no secrets stored; read only with `audit_logs.view` (**implemented, tested**; [ADR-012](../decisions/ADR-012-audit-log.md)). |
| T18 | **Security headers / HTTPS** | `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` everywhere; a deny-all CSP and `no-store` on API responses; HSTS on HTTPS requests; no storage route (**implemented, tested**). TLS itself is terminated at the proxy ([deployment.md](../deployment.md)). |
| T19 | **Identity confusion through database collation:** an email spelled differently (letter case, accents, invisible characters such as U+FE0F) still matches an account in MySQL, which can split throttle counters or route actions to the wrong account | Login accepts a database match only when the address equals the stored one apart from letter case. Reset emails always go to the stored address. Record IDs must be whole numbers (**implemented, tested**; FC-01, FC-07). |
| T20 | **Audit log tampering or flooding** | No API writes; the model refuses updates and deletes; throttled logins audited once per lock period (**implemented, tested**). Residual: the database user can still change rows (FC-12); no retention yet ([OQ-25](../open-questions.md#oq-25)). |
| T21 | **Unsafe production configuration** (debug on, log mailer, sync queue, wildcard CORS, wrong hash driver or cost) | `php artisan app:check-production` fails the go-live on each of these (**implemented, tested**; [deployment.md](../deployment.md)). |
| T22 | **Competitor intelligence:** a provider learns which other providers received the same request, or reads their threads, messages or offers | A provider sees the request and **only its own thread**; any other thread, its messages and offers return 404; the directory and the provider's views never list other recipients (**implemented, tested, mutation-verified**) |
| T23 | **Workflow tampering:** a client sets a status, re-opens a final thread, accepts a stale or superseded offer, accepts twice, or races two actions | Status changes only through action endpoints; `canBecome()` on both state enums (409 otherwise); row locks in a fixed order (request, then threads) inside one transaction with the audit entry; `based_on_version` for offers; only the latest offer can be accepted (**implemented, tested, mutation-verified**). Residual: concurrency is verified by the lock sequence, not by two truly parallel requests ([RK-23](../implementation-plan.md#5-risk-register)). |
| T24 | **Ineligible or suspended providers in the marketplace:** a request reaches a provider that is not approved, does not offer the service or does not target the factory's sectors; a suspended provider keeps negotiating | Eligibility checked in validation and again inside the transaction with the provider rows share-locked (CR-27); while the provider is not approved its threads are paused with 409 (CR-26, PROPOSED [OQ-40](../open-questions.md#oq-40)) (**implemented, tested, mutation-verified**) |
| T25 | **Exposure of negotiation content to IMC staff, the audit log or operators** | Administrators see request and thread statuses only; messages and offers return 403 to them (PROPOSED, [OQ-39](../open-questions.md#oq-39)); the audit log never stores message text, offer terms or prices (**implemented, tested, mutation-verified**). Residual: database operators can read the tables. |
| T26 | **Existence oracle:** an outsider distinguishes existing from missing requests or threads by getting 422 instead of 404 | Authorization runs in the Form Request, before validation, on every marketplace action and list (CR-28) (**implemented, tested, mutation-verified**) |
| T27 | **Directory scraping of contact data** | The directory shows company name, website, years, sectors and services only; it is limited to factory members (their eligible providers) and administrators; paginated, at most 100 per page (**implemented, tested, mutation-verified**; visibility PROPOSED, [OQ-37](../open-questions.md#oq-37)) |
| T28 | **Self-approval or approval tampering by provider members** | Approval fields are not mass-assignable and are ignored on profile updates; the approval endpoint needs `service_providers.approve` (own member 403, others 404); every decision is audited with its reason (**implemented, tested, mutation-verified**) |
| T29 | **Negotiation spam and oversized input** | Messages 30 per minute and offers 10 per minute per user; texts at most 5000 characters; at most 20 providers per request; reasons at most 2000 characters (**implemented, tested**; technical defaults) |
| T31 | **Forged or replayed payment callbacks** marking an invoice paid | The callback route is public but answers 404 for any key but the configured gateway's (none is configured). The adapter must verify the signature; an unverified body gets 400 and nothing is recorded. Each gateway event id is stored once (unique), so a replay is a `duplicate`. A different amount or currency changes nothing. Only `PaymentProcessor` changes payments, under locks (invoice, then payment) (**implemented, tested with a test-only fake adapter**; no real adapter exists yet) |
| T32 | **Double charge** by a retried or concurrent payment start | A required `Idempotency-Key`, unique per invoice; the invoice row locked while the payment is created; at most one pending or succeeded payment per invoice; the gateway called once per new payment (**implemented, tested**) |
| T33 | **Unapproved financial rules or figures** used in production | Every money rule is a setting with no default (issuer, numbering, tax, revenue share, gateway; also evaluation scale and pass mark). Unset, the operation answers 409 `policy_not_configured`; `app:check-production` fails on an invalid value (**implemented, tested**) |
| T34 | **Duplicate or missing invoice numbers** | Numbers come from a sequence row locked for the issuing transaction; unique index on `invoices.number` (**implemented; lock order tested**). Residual: not tested with truly parallel requests (RK-23). |
| T35 | **Agreement terms, prices and training plans visible to IMC** contrary to the negotiation-privacy interim | Agreements and contracts show IMC their existence and status only. Invoices are visible to IMC billing oversight (`invoices.view_any`, PROPOSED, to be confirmed with [OQ-39](../open-questions.md#oq-39)) (**implemented, tested**) |
| T30 | **Fabricated scores or financial artefacts presented as official** | No score column (classification `score` is always null); an agreed offer creates no contract, invoice or payment, and a test checks no such table or field appears; prices are labelled informational (**implemented, tested, mutation-verified**) |
